# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 사용하는 기술

`PRD.md` 10장에서 정한 구성을 따릅니다.

| 구분 | 기술 | 역할 |
| --- | --- | --- |
| 화면 | React (Vite로 시작, JavaScript) | 사용자가 보는 화면. 서버에 요청해서 기록을 보여줌 |
| 서버 | Python, FastAPI | 규칙과 권한을 검사하고 데이터를 저장함 |
| 데이터베이스(실제) | Supabase | 실제 서비스의 데이터 저장 |
| 데이터베이스(개발·테스트) | SQLite3 | 내 컴퓨터 개발과 자동 테스트 |

### 사용할 주요 패키지

꼭 필요한 패키지만 사용합니다. 아래에 없는 패키지를 추가하려면 먼저 이유를 설명하고 확인받습니다.

| 영역 | 패키지 | 사용 이유 |
| --- | --- | --- |
| 서버 | FastAPI, Uvicorn | 서버 본체와 개발 서버 실행 |
| 서버 | Pydantic, pydantic-settings | 입력값 검사와 `.env` 설정 읽기 |
| 서버 | SQLAlchemy, Alembic | SQLite와 Supabase에서 같은 코드로 저장하고, 테이블 변경 이력 관리 |
| 서버 | psycopg | Supabase(PostgreSQL) 연결. Phase 5부터 사용 |
| 서버 | 비밀번호 암호화 패키지, 로그인 토큰 패키지 | 비밀번호를 안전하게 저장하고 로그인 상태 유지 (Phase 3~4에서 구체적인 패키지를 정함) |
| 서버 테스트 | pytest, httpx | 서버 자동 테스트 |
| 화면 | React, React Router | 화면과 화면 이동 |
| 화면 테스트 | Vitest, React Testing Library, jsdom | 화면 자동 테스트 (jsdom은 테스트 안에서 브라우저 화면을 흉내 내는 데 필요) |

## 3. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- **모든 권한 검사는 서버에서 합니다.** 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다.
- **화면은 서버(FastAPI)에만 요청합니다.** 화면에서 Supabase에 직접 접근하지 않습니다.
- 비밀번호와 비밀 설정값(Supabase 접속 정보 등)은 코드와 화면에 쓰지 않고 `.env`에만 저장합니다. 채팅에도 붙여넣지 않습니다.
- 화면 환경 변수(`VITE_`로 시작하는 값)는 브라우저에 공개되므로 비밀값을 넣지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, `node_modules`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- 서버 코드는 SQLite와 Supabase에서 같은 결과를 내야 합니다. 어느 한쪽에서만 되는 기능은 쓰지 않습니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.

## 4. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/                 # FastAPI 서버
│  ├─ requirements.txt
│  ├─ alembic.ini
│  ├─ alembic/              # 테이블 변경 이력
│  ├─ app/
│  │  ├─ main.py            # 서버 시작점
│  │  ├─ core/              # 설정(.env), 비밀번호·로그인 처리
│  │  ├─ db/                # 데이터베이스 연결
│  │  ├─ models/            # 저장할 데이터(사용자, 기록, 댓글 등)
│  │  ├─ schemas/           # 입력·출력 형식과 글자 수 검사
│  │  ├─ routers/           # 기능별 요청 처리(auth, studies, todos, errors, public, comments, likes, reports)
│  │  └─ services/          # 권한 검사 등 공통 규칙
│  └─ tests/
├─ frontend/                # React 화면
│  ├─ package.json
│  ├─ index.html
│  └─ src/
│     ├─ api/               # 서버 요청 모음
│     ├─ pages/             # 화면(가입, 로그인, 홈, 공부 기록 등)
│     ├─ components/        # 공통 부품(카드, 버튼, 입력칸, 삭제 확인창)
│     └─ styles/            # CSS
├─ database/
│  └─ buildlog.test.sqlite3 # 개발·테스트용 데이터 파일, Git 제외
└─ docs/                    # 요구사항, 동작 설명서, 개발 문서
```

### 개발 중 사용하는 주소와 설정

| 항목 | 값 |
| --- | --- |
| 서버 주소 | `http://localhost:8000` |
| 화면 주소 | `http://localhost:5173` |
| 화면 → 서버 연결 | 화면 개발 서버가 `/api`로 시작하는 요청을 서버로 전달 |
| 서버 `.env` 항목 | `APP_ENV`, `DATABASE_URL`, `SECRET_KEY`, `CORS_ORIGINS` |
| 기본 데이터베이스 | `database/buildlog.test.sqlite3` (SQLite3) |
| Supabase 사용 | `DATABASE_URL`만 Supabase 주소로 바꿈 (Phase 5) |

## 5. 전체 개발 순서

| Phase | 만드는 결과 | 다음 Phase로 넘어가기 위한 핵심 조건 |
| --- | --- | --- |
| 0 | 개발 기준과 환경 확인 | 문서와 개발 환경에 충돌이 없음 |
| 1 | 서버(FastAPI) 뼈대 | 서버가 실행되고 상태 확인 요청에 응답함 |
| 2 | 화면(React) 뼈대 | 화면이 실행되고 서버와 연결됨 |
| 3 | 데이터베이스 연결과 사용자 테이블 | 첫 마이그레이션과 사용자 저장 테스트 통과 |
| 4 | 회원가입·로그인·닉네임 (서버 + 화면) | 회원 기능과 접근 제한 테스트 통과 |
| 5 | Supabase 연결 확인 | 같은 서버가 Supabase에서도 동작하고 외부 직접 접근이 막힘 |
| 6 | 세 가지 기록의 데이터 구조 | 저장·재실행·제약 조건 테스트 통과 |
| 7 | 공부 기록 전체 흐름 (서버 + 화면) | 공부 기록 기능만 단독으로 완성 |
| 8 | 할 일 전체 흐름 (서버 + 화면) | 할 일 기능만 단독으로 완성 |
| 9 | 오류 기록 전체 흐름 (서버 + 화면) | 오류 기록 기능만 단독으로 완성 |
| 10 | 공개 기록·공개 범위·공개 검색 | 비공개 유출 없이 공개 기능 동작 |
| 11 | 댓글 | 댓글 조건과 권한 테스트 통과 |
| 12 | 좋아요 | 중복 방지와 취소 테스트 통과 |
| 13 | 신고와 운영자 확인 | 신고 저장·중복 방지·일반 사용자 접근 차단 확인 |
| 14 | 반응형 화면과 공통 오류 처리 | 360px 이상 화면과 지정 브라우저 확인 |
| 15 | 전체 통합 확인과 실행 문서 | `spec.md`의 완료 조건 전체 통과 |

기능 Phase(4, 7~13)는 같은 Phase 안에서 **서버를 먼저 만들고 테스트한 뒤 화면을 연결**합니다.

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위와 기술 구성이 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. Python, Node.js, npm, Git의 설치 여부와 버전을 읽기 전용 명령으로 확인합니다.
4. SQLite를 Python에서 사용할 수 있는지 확인합니다.
5. FastAPI, SQLAlchemy, React, Vite 등 사용할 도구의 서로 호환되는 안정 버전 후보를 정리합니다.
6. 개발 서버 주소, 데이터베이스 파일 위치, 환경 변수 이름을 정리합니다.
7. 테스트 명령과 서버·화면 실행 명령을 문서에 기록할 준비를 합니다.
8. 아직 정하지 못한 확인 필요 항목(8장)을 사용자에게 하나씩 질문합니다.

#### 예상 변경 파일

- `docs/plan.md` (확인 결과 반영)
- 필요 시 실행 환경을 설명할 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위와 기술 구성이 충돌하지 않는지 확인합니다.
- 도구 버전을 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

---

### Phase 1. 서버(FastAPI) 뼈대 만들기

#### 목표

기능 없이도 서버가 실행되고 "정상 동작 중"이라고 답하게 합니다.

#### 작업

1. `backend/.venv` 가상환경을 준비합니다.
2. FastAPI, Uvicorn, pydantic-settings, pytest, httpx를 설치하고 정확한 버전을 `backend/requirements.txt`에 기록합니다.
3. `backend/app/main.py`에 서버 시작점을 만듭니다.
4. `.env`에서 설정을 읽는 `core/config.py`를 만듭니다. 항목은 `APP_ENV`, `DATABASE_URL`, `SECRET_KEY`, `CORS_ORIGINS`입니다.
5. 상태 확인 요청 `GET /api/health`를 만듭니다.
6. 화면(`http://localhost:5173`)에서 오는 요청만 허용하도록 CORS를 설정합니다.
7. `.env.example`에 항목 이름만 기록합니다. `SECRET_KEY`는 개발용 값을 `.env`에 생성합니다.
8. `.gitignore`에 `*.sqlite3`, `.pytest_cache/` 등 개발 중 생성되는 파일을 보완합니다.
9. 상태 확인 자동 테스트를 만듭니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/app/main.py`
- `backend/app/core/config.py`
- `backend/tests/test_health.py`
- `.env.example`
- `.gitignore`

#### 확인 방법

- 서버가 오류 없이 시작되는지 확인합니다.
- 브라우저에서 `http://localhost:8000/api/health`를 열면 정상 응답이 오는지 확인합니다.
- 자동 테스트가 통과하는지 확인합니다.
- `.env`가 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 서버와 상태 확인이 정상 동작해야 합니다.
- 아직 데이터베이스는 만들지 않습니다.

---

### Phase 2. 화면(React) 뼈대 만들기

#### 목표

화면이 실행되고, 서버와 연결되는 것을 확인합니다.

#### 작업

1. `frontend`에 Vite로 React 프로젝트를 만듭니다. (JavaScript)
2. React Router를 설치하고 화면 이동 틀을 만듭니다.
3. Vitest와 React Testing Library를 설치합니다.
4. `/api` 요청을 서버(8000번)로 전달하도록 개발 서버를 설정합니다.
5. 공통 화면 틀을 만듭니다: 밝은 배경, 위쪽 메뉴, 카드 모양, 버튼, 입력칸.
6. 처음부터 컴퓨터·휴대폰 크기에 맞게 정리되는 구조로 만듭니다.
7. 홈 화면에서 서버 상태 확인을 호출해 "서버 연결됨" 또는 "연결 실패"를 보여줍니다.
8. 화면 자동 테스트 하나를 만듭니다.

#### 예상 변경 파일

- `frontend/package.json`
- `frontend/vite.config.js`
- `frontend/src/App.jsx`
- `frontend/src/api/client.js`
- `frontend/src/components/`
- `frontend/src/pages/Home.jsx`
- `frontend/src/styles/`

#### 확인 방법

- 서버와 화면을 함께 실행한 뒤 브라우저에서 "서버 연결됨"이 보이는지 확인합니다.
- 서버를 끄면 "연결 실패" 안내가 보이는지 확인합니다.
- 브라우저 폭을 줄여도 메뉴와 카드가 깨지지 않는지 확인합니다.
- 화면 자동 테스트가 통과하는지 확인합니다.

#### 완료 조건

- 화면과 서버가 함께 실행되고 서로 연결되어야 합니다.

---

### Phase 3. 데이터베이스 연결과 사용자 테이블

#### 목표

SQLite로 저장되는 사용자 구조를 먼저 확정하고 첫 마이그레이션을 만듭니다. Supabase 연결은 Phase 5에서 합니다.

#### 작업

1. SQLAlchemy와 Alembic을 설치하고 `app/db`에 데이터베이스 연결을 만듭니다.
2. 기본 `DATABASE_URL`은 `database/buildlog.test.sqlite3`로 둡니다.
3. SQLite에서도 테이블 사이의 연결(외래 키)이 지켜지도록 설정합니다.
4. 사용자 테이블을 만듭니다: 이메일, 암호화된 비밀번호, 닉네임, 가입 날짜·시간.
5. 이메일은 필수이며 중복되지 않게 합니다. 닉네임도 필수이며 중복되지 않게 합니다.
6. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용합니다.
7. 비밀번호 암호화 방식을 정하고 비밀번호 원문은 저장하지 않게 합니다.
8. 첫 마이그레이션을 만들고 빈 SQLite 파일에 적용합니다.
9. 자동 테스트는 매번 새 임시 SQLite 데이터베이스를 사용해서 개발용 데이터와 섞이지 않게 합니다.
10. 사용자 저장 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/db/`
- `backend/app/models/user.py`
- `backend/app/core/security.py`
- `backend/alembic.ini`, `backend/alembic/`
- `backend/tests/conftest.py`
- `backend/tests/test_user_model.py`
- `database/buildlog.test.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.
- 마이그레이션을 처음부터 다시 적용해도 같은 구조가 만들어지는지 확인합니다.

### Phase 4. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업 — 서버

1. 회원가입 요청을 만듭니다: 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
2. 이메일과 닉네임의 앞뒤 공백을 제거합니다.
3. 로그인 요청을 만듭니다. 이메일 또는 비밀번호가 맞지 않으면 "로그인 정보가 맞지 않다"고 응답합니다.
4. 로그인 상태를 유지하는 방식을 구현합니다. (방식은 8장 T1 확인 후 확정)
5. 내 정보 확인 요청과 로그아웃 요청을 만듭니다.
6. 닉네임 변경 요청을 만듭니다. 본인 닉네임만 바꿀 수 있습니다.
7. "로그인한 사용자만 접근"을 검사하는 공통 장치를 만듭니다. 이후 모든 기록 요청에서 사용합니다.
8. 서버 자동 테스트를 작성합니다.

#### 작업 — 화면

1. 회원가입 화면, 로그인 화면, 내 기록 홈 화면, 계정 설정 화면을 만듭니다.
2. 회원가입 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
3. 로그인 실패 시 이메일은 유지하고 비밀번호만 지웁니다.
4. 회원가입 성공 시 로그인 화면으로, 로그인 성공 시 내 기록 홈으로 이동합니다.
5. 로그인하지 않은 사용자가 보호된 화면에 접근하면 로그인 화면으로 이동시킵니다.
6. 위쪽 메뉴에 로그아웃 버튼을 만듭니다. 누르면 로그인 상태를 끝내고 로그인 화면으로 이동합니다. (T2 결정: 넣기로 함)

### Phase 5. Supabase 연결 확인

#### 목표

같은 서버 코드가 SQLite와 Supabase 두 곳에서 똑같이 동작하는지 확인하고, 데이터가 외부에서 직접 읽히지 않게 막습니다. 기록 기능을 만들기 전에 두 데이터베이스의 차이를 일찍 찾는 것이 목적입니다.

#### 작업

1. (사용자 작업) Supabase 프로젝트를 만들고 데이터베이스 접속 주소를 `.env`의 `DATABASE_URL`에 직접 입력합니다.
2. psycopg를 설치하고 서버가 PostgreSQL 주소를 인식하게 합니다.
3. Alembic 마이그레이션을 Supabase에 적용합니다.
4. **Supabase의 외부 직접 접근 차단**: 모든 테이블에 Row Level Security(행 단위 접근 제한)를 켜고 접근 허용 규칙을 만들지 않습니다. 서버만 데이터를 읽고 쓰게 합니다. 이 설정은 이후 새 테이블마다 마이그레이션에 포함합니다.
5. Supabase에 연결한 상태로 서버를 실행해 회원가입과 로그인을 직접 확인합니다.
6. 두 데이터베이스의 차이로 문제가 생기는 부분을 점검합니다: 이메일·닉네임 대소문자 비교, 날짜·시간대, 참/거짓 값.
7. 자동 테스트는 계속 SQLite만 사용합니다. 자동 테스트가 실제 Supabase 데이터를 건드리지 않게 합니다.
8. `.env.example`에 Supabase용 항목(이름만)을 보완합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/app/db/`
- `backend/alembic/versions/` (접근 제한 설정 포함)
- `.env.example`
- 필요 시 `docs/setup.md`

#### 확인 방법

- Supabase 화면에서 사용자 테이블이 만들어졌는지 확인합니다.
- Supabase에 연결한 서버로 가입·로그인이 되는지 확인합니다.
- Supabase가 기본 제공하는 공개 키로는 사용자 테이블을 읽을 수 없는지 확인합니다.
- Supabase에서 비밀번호가 암호화된 값으로만 저장되어 있는지 확인합니다.
- `DATABASE_URL`을 SQLite로 되돌려도 서버와 자동 테스트가 그대로 동작하는지 확인합니다.
- `.env`와 Supabase 비밀값이 Git 기록 대상에 없는지 확인합니다.

#### 완료 조건

- 두 데이터베이스에서 회원 기능이 같게 동작해야 합니다.
- Supabase 데이터를 외부 공개 키로 읽을 수 있으면 다음 Phase로 넘어가지 않습니다.

4. 삭제는 확인창에서 동의한 경우에만 요청합니다.

### Phase 10. 공개 범위·공개 기록·공개 검색

2. 다른 사용자의 공개 기록을 읽는 화면을 만듭니다. 수정·삭제 버튼은 보이지 않습니다.

### Phase 11. 댓글 기능

#### 목표

공개된 공부 기록과 오류 기록에서만 댓글을 사용하게 합니다.

#### 작업 — 서버

1. 댓글 테이블을 만듭니다. 댓글은 공부 기록 또는 오류 기록 중 **정확히 하나**만 가리키게 제한합니다.
2. 마이그레이션을 만들고 접근 제한 설정(Phase 5)을 포함합니다.
3. 댓글 작성, 목록, 수정, 삭제 요청을 만듭니다.
4. 댓글 내용은 1~500자로 검사하고 앞뒤 공백을 제거합니다.
5. 댓글은 오래된 순서로 보냅니다.
6. 댓글 작성자는 자신의 댓글을 수정·삭제하게 합니다.
7. 기록 작성자는 자신의 기록에 달린 댓글을 삭제하게 합니다.
8. 공개 할 일에는 댓글 요청 경로를 제공하지 않습니다.
9. 기록이 비공개가 되면 댓글 데이터는 유지하되 다른 사용자에게 숨깁니다. 다시 공개하면 보여줍니다.
10. 작성자의 현재 닉네임을 댓글에 포함합니다.

#### 작업 — 화면

1. 공개 공부 기록·오류 기록 상세 화면에 댓글 목록과 입력칸을 추가합니다.
2. 내 댓글에는 수정·삭제 버튼을, 내 기록의 댓글에는 삭제 버튼을 보여줍니다.
3. 삭제 확인창을 보여줍니다.
4. 실패 시 입력 중인 댓글을 유지합니다.
5. 공개 할 일 화면에는 댓글 영역이 없습니다.

### Phase 13. 신고와 운영자 확인

#### 목표

로그인 사용자가 공개 기록이나 댓글을 신고하고, 일반 사용자는 신고 내용을 볼 수 없게 합니다.

#### 작업 — 서버

1. 신고 테이블을 만듭니다. 신고 대상은 공개 공부 기록, 공개 할 일, 공개 오류 기록 또는 댓글 중 **정확히 하나**로 제한합니다.
2. 신고 이유는 1~500자로 검사하고 앞뒤 공백을 제거합니다.
3. 한 사용자가 같은 대상을 한 번만 신고하게 데이터베이스 제약을 둡니다.
4. 신고 요청을 만들고, 이미 신고한 대상이면 그렇게 안내합니다.
5. 신고만으로 대상 기록이나 댓글을 자동 삭제하지 않습니다.
6. 신고 데이터를 **일반 사용자에게 보내는 요청은 만들지 않습니다.** 운영자 확인 방법은 8장 T3 결정에 따릅니다. 기본안은 Supabase 화면에서 직접 확인하는 방식입니다.
7. 대상 기록이 비공개가 되어도 신고 기록은 유지합니다.
8. 별도의 신고 처리 상태 기능은 만들지 않습니다.

#### 작업 — 화면

1. 공개 기록과 댓글에 신고 버튼을 추가하고, 신고 이유 입력 창을 만듭니다.
2. 신고 성공과 실패 안내를 보여줍니다.
3. 실패 시 입력한 신고 이유를 유지합니다.

#### 예상 변경 파일

- `backend/alembic/versions/`
- `backend/tests/test_reports.py`
- `frontend/src/components/ReportDialog.jsx`

#### 확인 방법

- 신고 이유의 0자·1자·500자·501자를 확인합니다.
- 같은 사용자의 중복 신고가 차단되는지 확인합니다.
- 신고 후 대상이 자동 삭제되지 않는지 확인합니다.
- 서버가 신고 목록이나 내용을 돌려주는 요청이 어디에도 없는지 확인합니다.
- 비공개 전환 후에도 신고 기록이 남아 있는지 확인합니다.

## 7. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 결과와 확인 내용을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
